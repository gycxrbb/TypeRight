# 功能规格：同类选择（格式签名匹配）

## 概述

光标点进一个段落 → 全文所有"格式相同"的段落一起选中（黄色高亮）→ 浮条批量改格式。

## 签名模型

5 锚点 × 4 维度，取段落可见区间的首字符、25%、50%、75%、尾字符：

| 维度 | 首尾锚 | 中段3锚 | 备注 |
|---|---|---|---|
| 中文字体名 | ✅ | ❌ | Font.Name* 对部分区间有读取抖动 |
| 西文字体名 | ✅ | ❌ | 同上 |
| 字号 | ✅ | ✅ | |
| 加粗 | ✅ | ✅ | |
| 颜色 | ✅ | ✅ | |
| **主导字符类型** | ✅（单元级） | — | 中文 / 字母 / 数字 / 混合，2026-11 新增 |

**不参与比对**：对齐方式（黄金取证依据）、斜体（仅展示）、下划线/删除线/着重号（仅应用端）。

**未知值语义**：Word COM 读数抖动时产生"未知"值（如 Bold=9999999），未知 ≠ 任何值（宁漏勿错）。

## 主导字符类型维度（2026-11）

### 要解决的问题

文档把**数字/字母也设成同一字体字号**后，纯数字段、纯字母段与中文正文段在
字体/字号/加粗/颜色全同 —— 严格模式下互相判为同类，批量改格式时数字字母段被一起改掉。

实测（`TypeRight.Acceptance.exe charclass`，6 段全设宋体+Times New Roman+10.5pt）：

| 修复前 | 修复后 |
|---|---|
| **10 组两两互相判为同类** | **3 组**，且全部是"含汉字"的段之间 |

### 为什么不靠 Font.NameAscii 判断

实测 Word 会**按内容自动归一化**：纯中文段没有西文字符时 `NameAscii` 回落到中文字体（宋体），
有西文字符时才是 `Times New Roman`。这是渲染回落，不代表作者意图；主题字体下中西文名还可能完全相同。

→ 必须直接看**字符本身**。`CharClassDetector.Detect(string)`，纯字符串运算，**零 COM 成本**。

### 匹配粒度：整段判定 + 字符级刷写（2026-11 终定）

用户确认的需求口径：**"汉字归汉字、数字归数字"**——段内的数字/字母在视觉上保持原样
（不被高亮、不被改格式），但匹配仍以整段为单位。

实现方式：**匹配粒度不变，刷写粒度细化**。

| 环节 | 粒度 |
|---|---|
| 签名 / 匹配 / 命中计数 | 整段（不变） |
| 高亮染色 | **只对该字符类型的连续片段** |
| 批量改格式 | **只对该字符类型的连续片段** |

目标类型 = 用户光标/选区落在的那个字符的类型（`SelectSession.TargetClass`）：
点汉字 → 只动汉字；点数字 → 只动数字；落在标点/空白 → 不过滤（退回旧行为）。

底层是 `CharClassDetector.SplitByClass` / `FilterRuns`（纯字符串运算，零 COM），
被 `SimilarSelector.ApplyUnits(onlyClass)` 与 `BatchFormatter.ApplyUnits(onlyClass)` 各读一次文本后切分。

真机实测（`clsverify`，考察报告第 5 段 177 字）：

| 点击位置 | 汉字 | 数字 |
|---|---|---|
| 点汉字 | 14→**20pt** | **保持 14pt** |
| 点数字 | **保持 14pt** | 14→**20pt** |
| 不过滤（旧行为） | 14→20pt | 14→20pt |

> **回归坑（已修）**：`FilterRuns` 第一版遇到异类片段只置 `has=false` 而没有 flush
> 已累积片段 → 前面所有片段丢失。真机表现为「过滤后什么都没改」（177 字段落只保留 1 个片段）。
> 自检 `三个中文片段全部保留` + xUnit `FilterRuns_KeepsAllMatchingRuns_NotJustLast` 锁死该行为。

### 判定口径：按主导类型

| 输入 | 结果 | 说明 |
|---|---|---|
| `这是中文正文段落` | 中文 | |
| `第1题下列说法正确的是` | 中文 | 汉字远多于数字 |
| `Python编程基础教程` | 中文 | 6 汉字 vs 6 字母 —— 英文词不该让整段脱离中文组 |
| `1234567890` | 数字 | |
| `abcdefghij` | 字母 | |
| **`2026年11月26日`** | **数字** | **汉字 3、数字 8 —— 数字压过汉字，判为日期段** |
| `ABC123` | 混合 | 无汉字且字母/数字等量 → 无主导者 |
| `，。！？` | 无 | 纯标点不参与 |

**判定顺序**（依据真实文档校准，不是拍脑袋）：

1. **数字压过汉字 → 数字段**。实测案例：`2026年11月26日`（汉字 3 / 数字 8）。
   这是日期落款段，与正文（汉字 114 / 数字 49）**字体字号完全相同**，
   只能靠字符组成区分。若按"有汉字即中文"，日期会被卷进正文被一起改格式。
2. **其余有汉字 → 中文**。`Python编程基础教程` 6:6 仍归中文。
3. **无汉字**：拉丁 vs 数字按数量比较，等量 → 混合。

> 历史取舍：第一版口径是"有汉字即中文"（更简单）。用真实文档验证后发现
> `2026年11月26日` 被误并入正文组，命中 13 处而非 12 处，故补充第 1 条规则。

### 实测验证（`tests/考察报告-商雨萤.docx`）

| 段 | 汉字/数字 | 判定 | 是否命中正文组 |
|---|---|---|---|
| 5 | 114 / 49 | 中文 | 是（正确） |
| 6 | 194 / 12 | 中文 | 是（正确） |
| 10 | 163 / 8 | 中文 | 是（正确） |
| 22 | **3 / 8** | **数字** | **否（修复前被误选）** |

修复前命中 **13** 处，修复后 **12** 处。

### 比对语义

- **严格模式默认参与比对**（用户确认：并进"严格"）
- 宽松模式可勾「忽略字符类型」关掉该维度
- **任一方为 `None`（未采集）→ 放行**。未知不该成为"不同类"的理由，
  否则旧调用点与读取抖动会造成漏命中（与字号/加粗的"未知不相等"不同：那些是数值抖动，这里是这一维根本没采）
- `FirstAnchorMatches` / `LastAnchorMatches`（混合段预筛）同样遵守该规则，否则预筛会把该命中的段筛掉

### 对既有验收的影响

讲义测试文档几乎全是中文段，主导类型天然一致 → **TC-01~05 计数无变化**（7/8/16 全部照旧）。
新增断言见 `DiagCharClass`（纯数字/纯字母零泄漏、中文段仍互判、维度可关）。

## 引导句感知

混合段落（行首标题句 + 正文同处一段）拆为两个独立匹配单元：

- **引导句单元**：段首到首个"非首锚格式"字符（顺序扫描，不用二分——岛状格式不满足单调性）
- **正文单元**：引导边界到段尾

用户光标位置决定匹配哪个单元（SampleOffset < leadBoundary → 引导句）。

## 分区隔离

正文样本只匹配正文段，表格样本只匹配表格内段落（`TableRanges` 位置判定）。防止 ★导读类装饰段被卷入。

## 公式区感知

`SimilarSelector.MathZoneRanges(doc)` 一次构建文档级 OMML 区间列表。所有签名锚点跳过区内字符——公式化后的文档匹配不退化。

性能注意：Word 用索引器枚举 OMaths（快路径），WPS 用底层 IEnumVARIANT 兜底（NetOffice 枚举器在两边的表现不同）。

## 宽松模式

浮条上可勾选"忽略字号/忽略颜色/忽略加粗"（可组合），勾选后实时重算（RecomputeMatches）。

默认严格模式（`Settings.StrictByDefault = true`）。

## 高亮机制

- 黄色 HighlightColorIndex 写入命中区间（**排除段落/单元格标记**——跨结束标记设置会扩散到整段）
- 包在一个 UndoRecord（"TypeRight 匹配标记"）内，Ctrl+Z 一次还原
- 会话关闭（Esc / 点击非命中段 / 文档关闭）时自动清除全部高亮

## 字体颜色板（浮条「A」按钮）

- **常用色** 6 色（柔和低饱和：黑/深蓝/中蓝/深红/深绿/灰）+ **标准色** 10 色（与 Word「字体颜色」标准色一致）
- **其他颜色…** 调系统取色器（ColorDialog，FullOpen 直接展开自定义区）；模态属主为宿主窗口
- 取色器自定义色板跨会话持久化（`settings.json → CustomFontColors`），确定/取消均记住
- 选中后走 `ApplyChanges(ColorRgb)`，与色板点选同一幂等写入链路

## 浮条字体/字号回显（2026-11）

同类选择生效后，浮条要与 Word「开始」选项卡一致地显示**当前选中同类的字体与字号**，而不是空下拉 + 纯数字。

### 字号：中文字号双轨显示

`ChineseFontSizes`（`Core/Formatting/`，纯逻辑无 Word 依赖，xUnit 直测）：

| 磅值 | 显示 | 磅值 | 显示 |
|---|---|---|---|
| 42 | 初号 | 14 | 四号 |
| 36 | 小初 | 12 | 小四 |
| 26 | 一号 | 10.5 | 五号 |
| 24 | 小一 | 9 | 小五 |
| 22 | 二号 | 7.5 | 六号 |
| 18 | 小二 | 6.5 | 小六 |
| 16 | 三号 | 5.5 | 七号 |
| 15 | 小三 | 5 | 八号 |

非标准档位（12.5、11、20…）仍显示数值——**不硬套**中文名。字号下拉里标准档位是"四号 / 14"双行对照，非档位单行数值，与 Word 下拉口径一致。

浮条按钮、下拉、悬停提示三处共用同一显示口径（`ChineseFontSizes.Label` / `Description`）。

### 字体：列表外字体显示原名

样本字体是**主题字体**（`+中文正文` / `+西文正文`）或已卸载字体时，它不在 `InstalledFontCollection` 里。
早先实现直接清空下拉 → 用户看到空框以为"没读到字体"。现在直接写 ComboBox 的 `Text` 显示原名
（不在 `Items` 里插临时项——可编辑后插入/移除会把用户看得见的列表搞脏）。

### 未知值一律不显示 0

`FormatSignature` 的 `SizePt=NaN` 表示未知，但**文本同类模式**的 `SampleSignature` 是 `default(struct)`，
`SizePt` 落在 `0`。浮条按"字号恒为正，非正数即未知"兜底（`IsUsableSize`），显示 `—` 而不是 `0`。
文本同类模式的浮条改读**首个命中处的真实格式**（`DisplaySignature`，经 `FormatSignatureReader.ReadRange`），
所以文本模式也能显示"四号 / 仿宋"这类真实值。

## 打字录入（字体 / 字号）

两个框都是 `IsEditable="True"` 的可编辑 ComboBox：既能打字，也能点箭头出候选。

### 字号：三类合法写法

解析在 `ChineseFontSizes.TryParse`（纯逻辑、xUnit 覆盖）：

| 写法 | 例子 | 结果 |
|---|---|---|
| 中文字号名 | `四号` `小四` `五号` | 14 / 12 / 10.5 |
| 数字磅值 | `14` `12.5` `20` | 原值 |
| 带单位 / 全角 | `14磅` `14pt` `１６` | 14 / 14 / 16 |

- **范围**：Word 允许 1~1638 磅；越界（`0`、`9999`）判为非法，**不悄悄截断**
- **非法输入**：还原显示 + Toast 提示，**绝不改文档**（静默套用某个默认值比报错更糟）
- **回车提交**；**Esc 放弃本次编辑**（不关整个会话）
- 提交后显示回中文档位名（打 `四号` → 14pt → 显示回 `四号`），来回一致

### 字体：回车 / 失焦提交

- 回车或离开输入框即应用（Word 同款行为）
- 只做基本合法性校验（非空、无控制字符、≤32 字符）——**不做"字体是否已安装"校验**：
  主题字体（`+中文正文`）本来就不在安装列表里，按存在性拒绝会把合法场景挡掉
- `IsTextSearchEnabled="False"`：否则每敲一个键就自动选中候选并立刻应用，等于边打字边刷全文格式

### Esc 的语义分层

打字中按 Esc = 放弃这次编辑；不在输入框时按 Esc = 关会话。低级键盘钩子（`EscHook`）和
`PreviewKeyDown` 两处都加了 `IsEditingText` 判断——否则用户想取消输入却把整个浮条关掉了。

## 定位（2026-11 修复）

两个坐标陷阱，都会让浮条落到屏幕外：

1. **`GetPoint` 对视口外段落返回负的文档坐标**（实测 -31493,-30951）→ `LooksLikeScreenPoint` 判否，退回 `CenterOverWordWindow`
2. **DPI 缓存毒化**：`PositionNear` 在 `Show()` 之前调用，那时没有 `HwndSource`，早先实现把兜底值 `1.0` **永久缓存**；
   125% 缩放下 `GetPoint` 的物理像素再也不换算，浮条定位到 918（屏高 864）。
   现在只在真拿到 DPI 时缓存，否则 `EnsureHandle()` + `GetDpiForWindow`（Win7 退回 GDI `DpiX`）现取

夹取基准改为 `Screen.FromPoint` 的**该显示器四边**（不再只夹左上），且"取锚点所在显示器"而不是"光标所在显示器"。
